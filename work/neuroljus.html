An open-source care system for autistic people who need full support, many of them non-speaking, and for their caregivers. A language model only proposes settings. A deterministic, tested planner writes the care protocol, and hard safety rules are enforced in code. It is a research prototype, not a medical device.

Evidence base

  • Autism research library: 1,710 open-access studies from Europe PMC. Every DOI is checked in Crossref and retracted papers are excluded. It includes 242 systematic reviews, 130 meta-analyses and 316 controlled trials.
  • Ten crisis protocols in Spanish, English and Swedish. Each uses an antecedent-behaviour-consequence log, treats the possible function of a behaviour (escape, request, sensory, pain) only as a hypothesis, and cites three to six studies from the library. A test checks that every citation exists.
  • A pre-data validation plan following TRIPOD+AI, with agreement against human annotators (kappa, intraclass correlation, Bland-Altman) and a bias audit across skin tones. It rules out emotion recognition.

Method: from plain language to a care protocol

  1. A local risk screen runs before any network call. Text about bleeding, self-injury or seizures produces a plan that only notifies the caregiver and logs the event, with the emergency number for the caller's country.
  2. Otherwise the language model receives the caregiver's description and must answer in a strict schema that contains settings only.
  3. Every setting outside the allowed values is dropped or clamped. Safety exceptions from the chosen scenario are a floor the model can add to but never lower.
  4. A deterministic planner writes the protocol and its export packets. The model never writes the protocol itself, and the planner is covered by determinism tests.
  5. If the model is unavailable, the closest preset is used.

The protocol vocabulary has 7 commands, 5 safety exceptions and 6 scenarios, and can be exported for 4 kinds of target.

The phone as the first body

Today the protocol runs on a phone. It can dim the screen, play brown noise at a capped volume, vibrate and show a visual card, while keeping a local log. A routine starts only when the caregiver presses Start, and Pause and Stop stay on screen. A sensory profile can only lower stimulation, never raise it.

NL-VISION: on-device signals

A camera layer runs in the browser with MediaPipe face and hand landmark models. It computes blink rate, mouth opening, face and hand movement, and hand-near-face, and stores one row per second on the device. It measures movement and landmarks, not emotions. Its thresholds are fixed by design and not yet fitted to data, as the validation plan states.

Privacy

  • Stays on the device: video, landmarks, the sensory profile, run records and the caregiver's pattern notebook.
  • Leaves the device: the caregiver's written description, the latest numeric camera summary, and an anonymous count of what helped. Logs record error types, never the text.

Quality

146 automated tests in 24 files cover the planner, the intent parser, the risk screen, profile fusion, the phone body, the signal maths, the library pipeline, the protocols and the voice line. Continuous integration runs the tests and a type check, and a guard blocks unreviewed changes to the core vision files. In a scripted evaluation, the voice line passed 38 of 42 scenarios.

Limitations

  • No physical robot is connected yet. The robot formats (ROS 2, MQTT, HTTP) are specified exports, not a working integration.
  • Rejection by the person is not detected automatically. Today the caregiver's Stop button is the stop.
  • The camera signals have not been validated, and no study with people has been done yet.
